# BLACKOUT v3.4 launch procedure — no deployment in this task

This supersedes every earlier launch guide. Existing deployments and the project's token are not upgraded, replaced or re-minted by this submission. Apply these steps only in the separately authorized launch process; if an immutable v3.3 instance is already live, this source cannot change it.

## Freeze and publish the configuration

Retain the selected custom v4 hook, zero LP fee, 10% swarm allocation, 70% AMM allocation (`poolBps=7000`), 20% reward endowment (200,000,000 tokens), fixed team `0x6d51cBE774aeAe4dd40bCA2560E9bc2695A0d007`, heartbeat 200 bps / 1 ETH cap, and 42-day drip. No team wallet is the primary remainder recipient.

Required inputs come from the accepted launch configuration, not test fixtures: existing/predicted token address, official pool manager, **the contract that is actually the sender to PoolManager.initialize**, network recipient, tick spacing, immutable application factory, swarm address, NFT root and snapshot block, and reserved application launch numbers/indices. Confirm 18 token decimals. Confirm the factory implementation is immutable and its predictor corresponds to its actual CREATE2 deployment; an address pin cannot make a lying or upgradeable external predictor trustworthy. No production address or factory upgrade assumption has been verified by this source-only job.

1. Format/build with unchanged compiler settings, run all tests, regenerate/check `src/lib/ModuleCode.sol`, then rebuild. Archive the exact compiler output; formatting Solidity changes metadata and can change pins. Regenerate `launch/V4Market.sol` with `forge flatten src/V4Market.sol` for standalone review. The deployed artifact must use the exact reviewed compilation, not an independently recompiled flatten with different metadata.
2. Predict/deploy Params with the accepted swarm and heartbeat values. Params takes `(swarmWallet,200,1 ether)`; deployment can happen before the game because constructors make no external calls. Its address is fixed before calculating the hook commitment.
3. Reserve the intended GameRegistry deployment coordinates `(registryLaunch:uint64, registryIndex:uint256)`. Compute `gameConfigHash = keccak256(abi.encode(params,starterRoot,snapshotBlock,endowment,registryLaunch,registryIndex))`. `script/PredictGame.s.sol:commitment` is the read-only helper. Token, hook and factory are verified separately. This deliberately excludes the hook address to avoid a CREATE2 cycle.
4. Hook constructor arguments, in order: `(manager,token,networkRecipient,uint24(0),tickSpacing,officialLauncher,applicationFactory,gameConfigHash)`. Eight arguments. Mine the address flag bits `0x10cc` with the supplied MarketFactory helper or the official launch process. No owner, initializer setter, tax setter, max buy or rebind exists.
5. With the hook address fixed, predict GameRegistry from its **seven** constructor arguments `(token,params,hook,starterRoot,snapshotBlock,endowment,applicationFactory)`. There is no timestamp constructor input. `launchTime()` reads the hook and reverts before authorized initialization. Predict RewardPool from `(registry)` at its reserved application coordinates. `PredictGame.predict` returns both addresses; it does not deploy or broadcast.
6. Publish the predicted RewardPool as the IMD launch **`remainderTo`**, with `poolBps=7000`. The ordinary ERC20 allocation can credit an address with no deployed code. The complete graph is tested locally by transferring principal before both registry and pool deployment.

**Platform precondition:** the official token prediction must be independent of `remainderTo`, and the official launcher must accept a future address and honor the reserved application coordinates. Neither property follows merely from ERC20 or our local factory fixture. Verify the real launch payload/prediction against official tooling before authorizing the token launch. Do not guess future launch numbers or claim the live route is verified. If token prediction depends on remainderTo or the allocator requires deployed code, use the explicit fallback below. No new token is launched to repair a prediction failure.

## Deploy, enroll, fund and open

Retain two application batches (8 + 4): Params, GameRegistry, RewardPool, FarmRewards, FarmCore, FarmItems, PackSale, StarterClaim; then FeeRouter, GridOperator, Season, FarmEngine. All ten modules have only `(registry)` in their constructor. Their roles are 0..9 in the order just listed after GameRegistry (FeeRouter=6). Use the actual accepted coordinates for each, not the local rehearsal's 1/2 or test 7/8/9 values.

1. The official launcher initializes precisely the hook's ETH/token pool. Any other sender reverts the entire initialization, so an attacker cannot warm the launch clock. One initialization anchors the immutable tax schedule and sales opening. Pinning the launcher means a launcher unable to use this custom hook is a launch integration failure, not something an owner can bypass.
2. Deploy the predicted application graph. Anyone calls `registry.register(role,actualLaunch,actualIndex,exactCreationCode)` for each role. Registration verifies the pinned compiler-specific creation-code hash and factory prediction and is write-once. Publish all ten Registered events.
3. Anyone calls `hook.bindFeeRouter(actualFeeRouter,registryLaunch,registryIndex)`. It validates the pinned configuration, canonical registry creation/address, factory, token, registry-to-hook back-reference and registered FeeRouter. Neither team nor swarm can substitute a look-alike or another canonical game. Binding may precede or follow initialization; fees collected earlier remain escrowed.
4. Anyone calls `RewardPool.fundEndowment()`. For the direct allocation this transfers nothing further: it accounts for the newly transferred, previously unaccounted principal. Check Endowed amount exactly 200M tokens, `endowed()==true`, `lockedEndowment()==200M`, and frozen 42-day drip. Ordinary donations, game spending and buybacks are separately tracked before funding and cannot counterfeit the principal. Do not call the removed `activateEndowment` selector.
5. Anyone flushes fees. During minutes 0–10 / 10–20 / 20–30 the **whole** 90% / 50% / 25% buy tax enters rewardETH, with no team/network share of that stepped tax. Thereafter buys pay normal 2.25%; sells always use the normal project/network fees plus progressive surcharge. There is no buy-size cap. Internal reward buys are disabled during launch tax and require a warmed 30-minute quote.
6. Start `advanceEpoch()` after initialization. Purchases open exactly at `hook.initializedAt()+3600`, provided the pool is endowed and the hook is bound to **that registry's FeeRouter**. Until both hold, ETH and token purchases revert atomically. Price pacing starts at that opening. No constructor timestamp can open early.

## Explicit fallback if predeployment allocation is unavailable

Prefer a platform-supported atomic transfer to the deployed predicted pool. If the official launcher cannot perform that, retain `fundEndowment` and publish the following separately approved custody steps before launch: identify the actual allocation recipient supplied by the requester in the launch record; allocate precisely 200M as a separately labeled reward obligation, publish its launch Transfer receipt; deploy/enroll the graph; that same recipient approves the missing principal to RewardPool and calls `fundEndowment()`. Publish approval, ERC20 Transfer and Endowed transaction hashes and reconcile the full 200M. A partial prior raw transfer reduces only the missing principal; ordinary accounted inflows do not. Packs remain closed until funding completes. Revoke unused allowance afterward. No zero/dead/test recipient is supplied here. This fallback has temporary recipient custody and is **not** equivalent to the primary custody-free route; it must be visible in the launch announcement. Existing v3.3 remainder transfers cannot be rewritten by this job.

## Operation and immutable limits

- Run the public entropy keeper in [entropy-v34.md](entropy-v34.md). Poll native blocks every two seconds; capture after target+1 and by target+256. Captured seeds survive indefinitely. Expiry re-arms unpaid and preserves the receipt; capture/resolve can be called by anyone. Wallet inventory does not block separate capture.
- Buybacks: at least five minutes apart; amount between `min(0.05 ETH,rewardETH)` and `BuyBatch` (default maximum 0.5 ETH). Use smaller admissible batches for thin liquidity. The quote already deducts normal fees; set `minOut >= quote*(10000-SlippageBps)/10000`, maximum slippage 150 bps. Failed execution restores balances and interval. Remaining ETH queues until a safe fill; do not disable the floor or assume every batch is executable.
- New mining starts with the first installed snapshot, weighted by the remaining epoch seconds. Later loadout edits remain next-epoch changes. No emission unlocks for an empty prefix. Owner actions maintain the 12-epoch commitment; sponsors may settle/resolve without privileged roles. Starter claims and token packs paid from pending rewards remain the no-upfront-ETH gameplay route apart from transaction gas.
- Swarm numeric changes retain a maximum 10% per key per 24 hours. The seven-day inflow rule is a public dry-run policy proposal, not autonomous governance; publish all seven completed-day cash pack totals and resulting letters. It cannot modify tax steps or sale opening.
- Only new PackSale ETH/token purchases pause. Maximum 72 hours; automatic expiry; next pause no earlier than original expiry plus 72 hours even after manual early unpause. Claims, withdrawals, sync, epoch advance, entropy, buybacks and season settlement have no pause checks.
- Before weekly deadline (week end + 7 days), settle the complete week. Best prize needs 20 active epochs and capped 1 ETH spend. Tickets cap committed hash at 100k/epoch and 2.8M/week. Prepare once after deadline, finalize using the committed future native block, or re-arm an expired target. Three unique lottery winners, pull-based item/pack claims; reserved best-prize tokens credit the winner or recycle when nobody qualifies. A failed finalization or full inventory rolls back without losing entitlement. Late settlement still pays mining but does not enter a closed competition.

The operator supplies transaction gas and any external policy-scheduler budget. Bounties are bounded, may be zero when heartbeat is empty, and are not a guarantee of service. Verify keeper inclusion latency, L2 data fees, oracle behavior, code sizes, factory immutability and the live initialization sender during the separately authorized final launch rehearsal. This task used local/offline execution, not a funded chain.
