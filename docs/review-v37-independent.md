# BLACKOUT v3.7 independent contributor review

Reviewed on 2026-10-11 by the second contributor, separately from the implementation pass. Scope: the v3.7 diff, authority graph, constructor/binding design, oracle protocol compatibility, recurring question policy, keeper/UI encoding, and targeted regressions. This is a bounded source and local-test review, not a comprehensive external audit. No deployment, broadcast, paid oracle request, schedule purchase, token transfer or mint was performed.

## Findings and disposition

1. **Launcher constructor encoding — resolved and retested.** The official worker release accepts at most 16 constructor argument strings, each one a static ABI word or an allowed address placeholder. Its encoder appends one 32-byte word per string; it cannot encode the original two SwarmDesk structs as two manifest arguments. Those structs occupied 21 ABI words. This was reported after the first successful focused test run. The repaired constructor takes 14 flat static words, packs the context window and binding coordinates with unused-high-bit rejection, and derives the fixed 1 ether heartbeat cap. The compiled ABI matches the worker validator; canonical initcode plus arguments is 20,450 bytes and deployed runtime is 17,157 bytes. The round-trip binding and invalid-packed-bit tests pass. Offline Solidity and JavaScript encoders document and check the same layout.
2. **Binding dependency cycle — resolved.** Committing the market address inside Desk's game configuration would introduce Desk → Params → market → Desk. Desk instead commits token, frozen roots/snapshot and endowment, verifies pinned Registry/Params creation code, and binds their exact reserved coordinates through the authenticated application factory. The market separately commits Params and the full Registry configuration. This relies on the official factory admitting each launch number once; an arbitrary permissionless CREATE2 factory is unsuitable. The local deployment fixture now models unique admission.
3. **Current-state observation and Robinhood finality lag — resolved.** The initial event definitions requested finalized game state while callbacks required the current epoch. A read-only RPC sample showed `finalized` approximately 1,209 seconds behind `latest` (`safe` approximately 849 seconds behind), which could make a question shortly after an epoch boundary permanently stale. The committed definitions now use one native latest-minus-five block, with an epoch recheck, and explicitly describe these as soft confirmations.
4. **Recurring question identity — resolved with an explicit policy constraint.** Relative windows produce a different question hash every run, while schedules freeze their input. The immutable questions use an absolute context anchor and ask for the current consumer's game state, with signed UTC slot/epoch fields. The receiver checks exact question commitments, protocol window, domain, panel, freshness and one-use UUID/transport/slot tracking. This permits a new answer to the same question in a later slot without admitting an unrelated payer's different question. Current-context questions are supported by an observed official public request; live panel admission and liveness remain launch responsibilities.
5. **Dormant modules — corrected before commitment freeze.** A permanently fixed policy that never announced dormant features would have removed their practical v3.6 activation path. The final policy keeps them dormant initially, then makes ids 0/1/2 eligible for oracle notice at minimum ages 90/120/150 days after the ordinary feature sequence. Weekly war/lot and conditional four-week collapse commands remain subject to all original gates. These timings are documented deployment-policy assumptions, not new module permissions.
6. **Launch artifacts — warning added.** Separately compiling the flattened market changes embedded Registry metadata/creation code and therefore authenticated predictions. The runbook requires accepted canonical Foundry artifacts for deployment and treats the flattened file as a source reference.
7. **Protocol signer terminology — clarified.** The live Intake transport writer differs from the EIP-712 attester. Desk checks the transport contract as caller and the verified attester as signer; it does not substitute `Intake.writer()` for the signing key.
8. **Cost arithmetic — corrected.** Four daily questions at 0.5 IMD plus one weekly question cost 14.5 IMD/week, approximately 2.07143 IMD/day. Thirty days containing five weekly runs cost 62.5 IMD. Optional backup asks can double that bounded weekly spend.

No additional exploitable authority bypass or answer encoding defect was found in the reviewed implementation. Callback receipt authenticates and stores; permissionless execution requires the exact committed bytes. Invalid calls cannot change the authority graph. Future-block randomness and economic behavior were inherited and were not redesigned by this review.

## Remaining limitations and launch responsibilities

No implementation blocker remains from this review; this does not authorize launch. Actual deployment roots, snapshot, token/hook and reserved coordinates must be supplied and reviewed; immutable values cannot be repaired by an administrator. The runbook requires a small Desk bootstrap plus the two eight-contract application jobs. It requires direct predicted RewardPool funding and stops launch if the launcher cannot provide it.

No owner or migration switch can rotate the oracle endpoint, attester, price ceiling or question policy. The five-seat/four-agreement panel and external attester remain trust assumptions. The transport writer may withhold, fail or mispair delivery; unsigned failures never authorize game actions. Any payer can fund the exact committed question, and any caller can spend the explicitly bounded backup quota. Paid failures have no refund. A separate authorized launch rehearsal must check current admission, consumer metadata, real callback routing, funding and keeper gas sponsorship. Native latest-minus-five observations remain sequencer-sensitive. Inherited entropy is not a VRF. These limitations are documented in [launch-v37.md](../launch-v37.md).
